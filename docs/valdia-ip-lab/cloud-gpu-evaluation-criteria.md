## 1. 目的とスコープ

### 1.1 目的

VALDIA IP Lab(新規事業)Phase 0 における蒼龍検証(画像生成・動画生成・LoRA学習)を、**物理GPUを購入せずに** クラウドGPU環境で実行するための選定基準を定める。さらに Phase 1 実装で **ローカル RTX 4090 中古ワークステーション** へ移行する際、同一ワークフローを再現できるよう、選定段階から **環境再現性** を担保する。

### 1.2 スコープ

| 区分 | 取扱範囲 | 備考 |
| --- | --- | --- |
| **自社IP / 天機-OS素材** | Phase 0 で扱う | クラウド検証可。ただし秘匿性確認項目を必ず満たす |
| **顧客IP素材** | Phase 0 では扱わない | 成約後にローカル RTX 4090 環境へ移行(原則)。Secure Cloud 利用時も顧客許諾と削除証跡を必須 |
| **物理GPU調達** | Phase 0 では行わない | Phase 1 実装移行判定後に RTX 4090 中古ワークステーションを調達 |

### 1.3 本書で扱わないもの

- ComfyUI / Wan 2.2 / Qwen-Image / Z-Image の **モデル選定および採用ライセンス確認**(指示書2で扱う)
- ワークフロー JSON / custom_nodes / 依存関係の具体的管理ルール(指示書2で扱う)
- 蒼龍のキャラクター設定およびプロンプト(指示書3・4で扱う)

## 2. 判断軸の優先順位(逸脱禁止)

クラウドGPU プロバイダおよびインスタンス種別の選定にあたっては、以下の優先順位を **常に** 守る。下位の軸は上位の軸を決して上書きしない。

```
[1] データ秘匿性
        ↓
[2] 環境再現性(クラウド → ローカル移行可能性)
        ↓
[3] GPU安定供給(在庫・予約・中断耐性)
        ↓
[4] GPU仕様(RTX 4090 24GB 以上)
        ↓
[5] コスト(時間単価 × 利用時間 + 永続ボリューム + 転送量)
```

### 2.1 各軸の意味と確認ポイント

| 順位 | 軸 | 確認ポイント | 失格条件(これに該当したらコスト無関係に不採用) |
| --- | --- | --- | --- |
| 1 | データ秘匿性 | データ削除手順・永続ボリューム暗号化・公開範囲・運営側ログ保存範囲・第三者(ホストオペレータ)アクセス可否 | 削除証跡が取得できない / 第三者によるストレージ閲覧が排除できない / 利用規約上、生成物・モデルが学習目的で再利用される可能性がある |
| 2 | 環境再現性 | Docker image 指定可否 / Python・CUDA バージョン固定可否 / ComfyUI commit ピン留め可否 / モデル・LoRA・workflow JSON の永続保存可否 | コンテナイメージを固定できない、または永続ボリュームに `models/`・`workflows/`・`custom_nodes/` を保存できない |
| 3 | GPU安定供給 | RTX 4090 / L40S / A6000 等の在庫頻度 / Spot 中断ポリシー / 予約(Reserved)可否 | 24時間以上の検証で常時中断、もしくは需給逼迫時に同等GPUへフェイルオーバー不可 |
| 4 | GPU仕様 | VRAM 24GB 以上 / FP16・BF16 サポート / NVENC(動画ワークフロー時) | VRAM 24GB 未満 |
| 5 | コスト | 時間単価 / 永続ストレージ単価 / Egress 単価 / アイドル課金有無 | (上位軸を満たした候補内で比較するための指標。これ単独で採否を決めない) |

### 2.2 「データ秘匿性」を最上位に置く理由

- 自社IP/天機-OS素材は VALDIA の事業基盤そのものであり、漏えい・学習再利用された時点で事業価値が毀損する。
- Phase 0 段階では顧客IPは扱わないが、選定時点で「顧客IPでも使えるかどうか」の **同じ物差し** で判定しておかないと、成約後に環境を作り直す手戻りが発生する。
- コスト・速度はあとから最適化できるが、漏えいは取り返せない。

## 3. データ取り扱い区分(必須記載事項)

### 3.1 自社IP / 天機-OS素材

| 項目 | 方針 |
| --- | --- |
| Community Cloud 利用 | **検証用途に限定して可**。本番納品物の生成には使わない |
| 確認必須項目 | (a) 永続ボリュームの暗号化方式、(b) インスタンス停止時のデータ削除手順、(c) スナップショット・バックアップの公開範囲、(d) プロバイダ運営側のログ保存範囲、(e) 利用規約上の「生成物・アップロード物の二次利用条項」の有無 |
| ログ保管 | プロンプト・seed・出力先パスは **VALDIA 側で別途管理** し、クラウド側のログのみに依存しない |
| 終了時 | 検証終了時は永続ボリュームを **削除し、削除レシート / API レスポンスをスクリーンショット保存** |

### 3.2 顧客IP素材

| 項目 | 方針 |
| --- | --- |
| Phase 0 | **扱わない**。Phase 0 のクラウド環境に顧客IP素材を置くことは禁止 |
| 成約後 | **原則ローカル RTX 4090 環境**(中古ワークステーション)に移行 |
| Secure Cloud 利用条件 | (1) 顧客から書面または契約条項で「Secure Cloud 利用」を許諾、(2) 契約書に Secure Cloud 名・リージョン・暗号化方式・削除手順を明記、(3) 検証終了時に削除証跡(プロバイダ発行のログまたは API レスポンス)を VALDIA 側で保管、(4) 顧客からの削除要請に X 営業日以内で応答できる体制 |
| 学習用途 | 顧客IPを学習データに使う場合は、契約書に **学習可否・学習結果(LoRA等)の権利帰属・契約終了後の取扱い** を明記する。これらが定まらない案件はクラウド学習を不可とする |

### 3.3 物理ローカル(RTX 4090 中古ワークステーション)

| 項目 | 方針 |
| --- | --- |
| 利用フェーズ | Phase 1 実装以降、および顧客IP素材を扱う案件 |
| 物理セキュリティ | 施錠された作業スペース / ストレージ暗号化(BitLocker または LUKS)/ 退社時シャットダウン |
| ネットワーク | 顧客IP素材取扱中は **外部ネットへのアウトバウンドを最小化**(モデルダウンロードは事前に完了させる) |
| バックアップ | 顧客IP素材は **オフラインバックアップ**(外付けSSD施錠保管)。クラウド同期は契約上許諾された場合のみ |

## 4. 比較対象プロバイダ

| プロバイダ | 区分 | 本書での扱い | 備考 |
| --- | --- | --- | --- |
| **RunPod Secure Cloud** | データセンター直営 | 主候補(顧客IP対応含む) | Tier3+ DC 配備、SLAあり |
| **RunPod Community Cloud** | 個人ホスト | 主候補(自社IP/検証限定) | 価格安、ホスト依存度高 |
| Vast.ai | マーケットプレイス | 参考比較 | 価格最安帯、ホスト多様性高、秘匿性審査要 |

> **注**: 各プロバイダの価格・在庫・規約は変動が大きい。本書の比較表は「判定の枠組み」を示すもので、実際の契約直前に **必ず公式サイト・利用規約・DPAを再確認** すること。

### 5.1 マーケットプレイス型(Vast.ai / RunPod Community Cloud)の共通注意

- ホスト個人/法人の身元・契約義務はプロバイダ運営とは別レイヤー。
- ストレージは物理的にホストのマシン上にあり、運営側からホストの内部閲覧を完全に排除する手段は限定的。
- 上記より、**顧客IP素材は不可**、自社IP/天機-OS素材も **検証用途限定** とする。

## 6. GPU仕様基準

| 項目 | 基準 |
| --- | --- |
| VRAM | **24GB 以上**(必須) |
| 推奨GPU(優先順) | RTX 4090 24GB / L40S 48GB / A6000 48GB / RTX 6000 Ada 48GB |
| 不可GPU | RTX 3090 以下 / VRAM 24GB 未満の全GPU |
| Wan 2.2 動画生成想定 | 24GB で動作するワークフロー構成のみ採用(指示書2で確定) |
| LoRA学習想定 | 24GB で完結する LoRA ランクで学習し、必要時のみ 48GB GPU を一時利用 |

> Phase 1 ローカル環境が **RTX 4090 24GB** であるため、Phase 0 検証も **24GB で完結する構成** を選ぶ。48GB に最適化された構成で Phase 0 を進めると、ローカル移行で動かない構成が紛れ込み、環境再現性が崩れる。

## 8. コスト試算モデル

> 本書では「**月額**」ではなく「**時間単価 × 利用時間 + 永続ストレージ + 転送量**」で試算する。Phase 0 はバースト的に使うため、月額固定の発想だと過剰見積もりになる。

### 8.1 試算式

```
試算コスト(/月)
  = (GPU時間単価 × 想定稼働時間)
  + (永続ボリューム単価 × 容量GB × 24h × 30日)
  + (Egress単価 × 想定ダウンロード量GB)
  + (モデル保存ストレージ単価 × モデル容量GB × 30日)
```

### 8.2 想定稼働時間(初期見立て)

| 用途 | 想定稼働時間 / 月 |
| --- | --- |
| ComfyUI 画像生成検証 | 30〜60 時間 |
| Wan 2.2 動画生成検証 | 20〜40 時間 |
| LoRA 学習(蒼龍) | 1セットあたり 4〜10 時間 × 試行回数 |
| 合計レンジ | 60〜150 時間 / 月(Phase 0 期間) |

### 8.3 永続ストレージの想定容量

| 種別 | 容量見立て |
| --- | --- |
| ComfyUI 本体 + custom_nodes | 5〜10 GB |
| 画像系モデル(Qwen-Image / Z-Image / SDXL系) | 30〜60 GB |
| 動画系モデル(Wan 2.2 / Ovi 等) | 50〜120 GB |
| LoRA学習素材・学習成果物 | 20〜50 GB |
| 生成結果(画像・動画) | 50〜200 GB(動画ありの場合大) |
| **合計** | **150〜400 GB**(動画用途あり時) |

### 8.4 試算時の注意

- Community Cloud のホスト変更で価格が変わるため、**契約直前の単価を必ず再取得** する。
- Egress(ダウンロード)が想定外に高くつく構成があるため、生成結果は **必要分のみダウンロード** し、検証中はクラウド永続ボリューム上で保持する。
- アイドル課金(GPU停止中もボリューム課金など)を見落とさないこと。

## 9. データ管理チェックリスト(契約・利用ごとに実施)

### 9.1 契約前チェック

- [ ] 利用規約の「アップロード物・生成物の二次利用条項」を確認した
- [ ] DPA / SOC2 / ISO 27001 等の有無と範囲を確認した(顧客IP取扱予定の場合は必須)
- [ ] データ削除手順(ボリューム削除・スナップショット削除)が公式に明文化されている
- [ ] 削除証跡(API レスポンス・ログ)を取得できる
- [ ] Egress 課金・アイドル課金の条件を理解した
- [ ] 自社IP/顧客IP の取扱区分(本書 §3)に整合している

### 9.2 環境構築時チェック

- [ ] 永続ボリュームを暗号化(または暗号化された前提を確認)
- [ ] モデルファイルは SHA256 を取得して `environment-manifest.md`(指示書2)に記録
- [ ] ComfyUI / custom_nodes は commit ハッシュで固定
- [ ] Docker image タグを `:latest` ではなく **明示バージョン or digest** で指定
- [ ] プロンプト・seed・生成条件を VALDIA 側ストレージへログ出力する設定にした

### 9.3 検証終了時チェック

- [ ] 生成物のうち保管対象を VALDIA 側ストレージへ持ち出した
- [ ] 不要な生成物・素材をクラウド側で削除した
- [ ] 永続ボリュームを削除し、削除レシート / API レスポンスを保管した
- [ ] インスタンスを完全停止した(課金停止確認)
- [ ] 顧客IP を扱った場合: 削除証跡を顧客向け報告に添付できる形で保管した

### 9.4 持ち出し手順チェック

- [ ] モデル / LoRA / workflow JSON / 生成物 / 環境マニフェスト一式が揃っている
- [ ] チェックサム検証(モデル・LoRA)を実施した
- [ ] 持ち出し先(ローカル or VALDIAストレージ)で同一ハッシュを確認した

## 10. 環境再現性チェックリスト(クラウド → ローカル移行)

> 本書段階での **設計レベル** チェックリスト。具体的な手順とテンプレートは指示書2で定める。

- [ ] クラウド側で使用した Docker image を、ローカルでも同一タグ / digest で取得可能
- [ ] Python・CUDA・PyTorch のバージョンが固定され、ローカルで再現可能
- [ ] ComfyUI 本体の commit ハッシュが固定されている
- [ ] custom_nodes 一覧(リポジトリURL + commit)が記録されている
- [ ] モデル一覧(ファイル名 + ハッシュ + ライセンス + 公式URL)が記録されている
- [ ] LoRA ファイルの命名規則と保存先が決まっている
- [ ] workflow JSON が VALDIA 側で管理されている(クラウド永続ボリュームのみに依存しない)
- [ ] プロンプト・seed・生成条件のログ形式が決まっている
- [ ] ローカル RTX 4090 24GB で動作する VRAM 制約を満たしている
- [ ] 移行リハーサル(ローカルマシン購入後の最初の72時間で、Phase 0 と同一の出力が得られるか確認する手順)が計画されている

## 11. Phase 移行判定条件(クラウド → ローカル)

以下を **すべて満たした時点で** Phase 1 実装移行および RTX 4090 中古ワークステーション調達を実行する。

| # | 条件 | 検証方法 |
| --- | --- | --- |
| 1 | 蒼龍 1体の品質が監修基準(指示書4)を満たした生成物が継続的に作れる | 監修チェックリストで合格率 80% 以上 |
| 2 | 同一 workflow JSON + 同一モデル + 同一プロンプト + 同一 seed で再現性がある | クラウド上で 3 回以上同条件再生成して同等出力 |
| 3 | environment-manifest が完成している | 指示書2のテンプレートに沿って全項目記入済み |
| 4 | 顧客案件パイプラインが見えている | 成約 1 件以上 or 確度の高い見込み 2 件以上 |
| 5 | クラウド継続コストがローカル投資の損益分岐点を超える見込み | §8 の試算で、6か月運用がローカル中古機+電気代を上回る |

> 上記 1〜3 を満たさずに 4・5 を理由に移行すると、**ローカル環境で動かない構成を抱えたまま物理投資する** リスクが高い。1〜3 は譲らない。
